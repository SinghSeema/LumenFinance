# Design Decisions

A decision log, not a tutorial. Each decision has a status: **Locked**, or **Provisional** until a bake-off or test settles it. Reasoning draws on the strategy discussion and the "EMI Voice Agent: Final Stack and Strategy Decisions" doc. Vendor latency and quality figures are vendor claims until measured here.

## 1a. Ideas considered and rejected

| Idea | Why rejected |
| --- | --- |
| Route short acknowledgments to a different TTS engine than the main voice | The borrower hears two voices in one call; naturalness is the largest grade weight. Cached fillers in the same voice (D-12) give instant acknowledgments instead |
| Turnaround target under 600ms | No measurement supports it. Targets stay at Q-01 until real API results exist |
| Separate "firm" and "soft hardship" conversation paths | Hardship already escalates by code (G-05); a "firm" path pulls toward pressure (G-03). One prompt plus code flags is simpler |
| Framing the agent as a "collections agent" in the prompt | Nudges tone toward pressure and may raise refusal risk on Haiku (open item, section 5) |
| Regex parsing of dates the model writes (for example "05/11") | Day/month order is ambiguous; the model never writes dates in this design (D-10, D-19) |
| Real payment-status lookups (Razorpay, UPI) | Out of scope; tools are mocks (D-15) |

## 2. What was borrowed from Woka (ideas only)

Environment-variable tuning of VAD without code changes, Langfuse for per-turn tracing, and prompt rules that keep output speech-clean. Everything else is rebuilt for this problem.

## 3. Expected trade-offs to report

- **Latency versus voice quality:** a faster TTS may sound worse in Hindi; the bake-off numbers and the listening test make the choice explicit.
- **Streaming versus guarding:** checking each sentence before TTS adds a small delay but catches threats and promises; unverified disclosure is already prevented by construction.
- **Short VAD stop versus cut-offs:** a lower stop time answers faster but risks cutting off mid-number; tuned by ablation.
- **Code gates versus flexibility:** hard stage gates make the agent safer and less free-form; the LLM keeps freedom within each stage.
- **Free versus paid:** free tiers are enough to explore, not to evaluate or to run a live interview.

## 4. Latency: what is measured and how it is reduced

The brief asks what was measured and how it was reduced. Measured: response gap from VAD stop to playback start, with per-stage times (STT final, LLM first token, TTS first audio), median and p90 over at least 30 voice turns (`LLD.md` section 13, M9). Levers, tried one at a time and reported with before and after numbers: shorter VAD stop time; streaming STT; Haiku-class model with a short prompt (prompt caching if available); sentence-level streaming into TTS with a short first clause; warm TTS WebSocket; cached greeting, fillers and closing lines; no output guard work beyond a few milliseconds. Estimates in the strategy doc (about 850 to 1,400ms) are not results.
